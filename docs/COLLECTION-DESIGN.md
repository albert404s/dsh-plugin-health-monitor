# 采集控制与榜单范围

## 本轮方案

网站继续静态部署，不新增后台。顶栏“数据更新”让维护者选择手动采集或保存采集设置，然后前往 GitHub Actions 登录并确认。GitHub 需要仓库写入权限；网站不接收、保存或内嵌访问令牌。

- refresh：保存本次目标和预算，采集一次GitHub/npm/OSV数据。
- pause：兼容旧请求，记录自动采集关闭，不调用数据API。
- resume：不再对外提供；旧请求也保持自动采集关闭。
- configure：保存每轮插件上限、请求预算和 GitHub 预留额度；不改变定时开关，也不立即采集。
- 刷新已发布数据：仅重读网站 JSON，与重新采集不同，不消耗 GitHub 采集额度。

控制状态以 data 分支 collection-control.json 为准，随网站一起发布。网站上的状态是发布时快照，执行结果以 GitHub Actions 为准。旧data分支缺少控制文件时默认关闭；有文件但格式错误时阻止操作，不能当作自动恢复。

定时触发已删除，旧定时事件也无法通过控制检查。采集只由维护者手动发起；网页检查快照不触发采集。

## API 会不会不够用

会有限制，但不是终生累计额度。GitHub 主额度按小时恢复，还会因短时间过密请求触发额外限制：

| 认证方式 | 通常主额度 |
|---|---|
| 未登录 | 同 IP 每小时 60 次 |
| 个人访问令牌 | 每用户每小时 5,000 次，可能与其他应用共享 |
| 当前 Actions 的 GITHUB_TOKEN | 每仓库每小时 1,000 次 |

每个插件要查询仓库、提交、Issue、PR 和版本记录，分页与重试会增加请求。当前 20 个插件不代表只需 20 次请求，数量限制也不能保证一定不超额。已实现分页上限、有限重试、共享请求预算、旧快照保留和 GitHub 公共 GET 跨轮条件缓存；用量记录在 collection-report.json。

npm 与 OSV 同样不能视为无限服务，遇到 429/限流应退避。Python 改写不会增加平台额度，也不应用来绕过限制。手动采集应避免连续重复运行。

核对日期：2026-10-22。额度以服务端响应头和平台文档为准：
[GitHub 额度](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、
[GitHub 搜索限制](https://docs.github.com/en/rest/search/search)、
[手动运行工作流](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。

## “前 N 名编辑器”能否实现

可以，但应拆成两个功能：

1. **榜单设置**：在已收录的快照中选排序维度、筛选条件和前 N 项。完全在浏览器计算，不额外请求采集 API。已在插件库“榜单设置”实现前 N 项，支持预设和1–1000自定义，URL保存；先筛选排序再取N，分页只覆盖这份榜单。
2. **采集范围**：维护者指定搜索条件、候选数量 M 和每轮请求预算，再核验候选是否真是可安装的 DSH 插件。按 Stars 获取候选是可行的；“维护活跃度”是本站计算结果，必须先收集足够的指标再排名，不能直接向 GitHub 要这个榜单。

GitHub 单次搜索最多提供 1,000 条结果，搜索还有独立速率限制，也可能返回不完整结果。不能把关键词检索到的仓库自动当作有效插件，更不能称为全 GitHub 的完整榜单。npm 下载排序也需要先核实仓库与包的映射。

当前提供已收录插件的前 N 项展示，以及已核验清单的分轮采集上限；扩充到自动搜索时，再增加候选预览与身份核验。榜单数量 N、采集上限 M 和请求预算分别设置，缺数不当作低分。

2026-10-22 本轮已实现：展示数量 N；已核验清单采集上限 M（含轮换）；每轮请求预算与GitHub预留；跨轮公共GET验证缓存。自动搜索发现与候选核验编辑器仍未实现，不把已核验清单采集误称为全GitHub发现。
