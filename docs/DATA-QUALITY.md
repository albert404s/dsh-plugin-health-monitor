# 数据质量与契约

顺序为采集 → 清洗校验 → 评分 → 快照。评分公式仍由 src/lib/scoring.ts 的 1.1.0 实现，本次未改公式。

## 集中实现

- src/lib/contracts.ts：Zod 契约，采集种子、发布快照、历史、状态共用。计数为非负安全整数，不把非法值转换成零；保留超过 32 位范围的真实计数。
- src/lib/data-quality.ts：纯函数实现 GitHub 地址规范化、UTC 日历、日下载去重与冲突隔离、完整日窗口求和。
- scripts/lib/clean.ts：评分前身份核验、可选字段降级、窗口一致性、必要字段损坏时同身份历史回退，以及平台零值保护。
- src/lib/downloads.ts：前端展示复用相同日序列规则。相同日期只贡献一次包覆盖；疑似平台缺失只遮蔽零值，该日其他包的正值继续有效。

npm 汇总与日序列来自两个 API。完整且相同窗口的合计不一致时记录原因，保留两份原始证据；不擅自选择较大的值。新增可选 npm.quality 对象保存 rawDaily、冲突日、非法记录数、说明与 UTC 窗口边界。对旧 schema v1 快照向后兼容。

## 规则

同日同值保留一个；同日不同值整日不可用，不相加。非法日期、负数、小数、非有限值与窗口外记录隔离。缺少任何一天的 7 日窗口返回 null。跨月、跨年与平均值均按 UTC 日历处理。

至少 5 个已核验包有记录，且其中至少 80% 报告零值时，视为“疑似平台统计缺失”。这个推断不证明平台发生故障，不删除原始观测；该日正值不受影响，单个真实零值继续计入平均。

GitHub 新 Issue/PR 的窗口为采集时点往前 90 天至采集时点，提交为往前 30 天；边界按实际 UTC 时间比较，不信任未来或无效时间。公开 Release 按发布时间排序。关闭/合并数不能超过同一窗口样本。

重复 ID、仓库和已核验 npm 映射不能重复统计。必要字段损坏时隔离；已有同一 ID 且仓库身份相符的有效历史时，保留原时间并标记 stale。可选日期或下载字段损坏时降级为缺失并给出说明。采集全部失败或清洗后无有效记录时，不覆盖 latest/history。

存储严格校验发布数据与汇总；历史复用 parseHistory 去重、排序并隔离冲突，stale 记录不追加新的历史点。前端坏记录、坏历史与核心快照失败分别处理；刷新核心失败保留上次已加载快照。前端的回退仅在当前页面会话中保留，不增加持久缓存或数据库。

## 复现

npm test 检查计数边界、UTC 日历、冲突日、缺日、映射错配、同身份回退、写入失败保留旧快照和历史局部降级。npm run assess:model 对真实快照重放清洗与评分，报告见 SCORING-REVIEW.md。未来迁移 Python 时，应以这些输入/输出边界为契约用例。
