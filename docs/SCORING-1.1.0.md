# 健康评价规则与局限

版本：**1.1.0**（代码常量 `SCORE_METHOD_VERSION`）

本项目输出三个独立维度，不合成单一的“软件质量总分”：

1. **人气指数**：关注度与经核验使用量的相对位置。
2. **维护健康度**：近期公开维护活动的相对强弱。
3. **风险提示**：需要阅读的公开信号，不是安全审计结论。

另设 **数据完整度** 表示画像有多少证据，不参与质量判断。

## 1. 人气指数

### 归一化

对每个有效值 `x`：

```text
normalized = 100 * (log10(1 + x) - min(log10(1 + x))) / (max(log10(1 + x)) - min(...))
```

- 有效样本只包含本次实际有值的插件；缺失值不进入 min/max，也不补 0。
- 若所有有效值相同，归一化为 50，避免制造虚假差异。
- 多值等级使用同一快照内相对位置，因此新增/移除插件会改变分数。

### 权重

| 分项 | 有可靠 npm 数据 | 缺少 npm 数据 |
|---|---|---|
| GitHub Stars | 45% | 100%（归一化后） |
| npm 近 30 天下载 | 55% | 不参与 |
| 证据覆盖 | 100% | 45% |
| 置信度 | 高 | 中 |

缺少下载量时不会把下载量当作 0；但该插件不会进入四象限定位，因为横轴证据不完整。

## 2. 维护健康度

### 分项权重与算法

| 分项 | 设计权重 | 原始值 → 0–100 | 缺失/小样本 |
|---|---:|---|---|
| 最近代码提交 | 30% | ≤7d=100，≤14d=92，≤30d=82，≤60d=68，≤90d=55，≤180d=38，≤365d=20，更久=6 | 无提交日期则剔除 |
| 近 30 天非合并提交频率 | 15% | 0=12，1=38，2–3=55，4–7=72，8–11=88，≥12=100 | 分页达到上限时按已取得的下限计分，不整项剔除 |
| 近期 Issue 关闭率 | 20% | 关闭率 × 100 | n<5 时按 n/5 折减；0 条新 Issue 不参与 |
| 开放 Issue 积压 | 10% | 有开放 Issue 时：100 − (openNow / opened90d) × 100 | 按 openNow/5 折减；无开放 Issue 不参与 |
| 近期 PR 合并率 | 15% | 合并率 × 100 | n<3 时按 n/3 折减；PR 功能不可用则剔除 |
| 最近版本发布 | 10% | ≤30d=100，≤60d=92，≤90d=80，≤180d=62，≤365d=40，更久=18 | 没有稳定 Release 则剔除，不扣分 |

### 汇总

被包含分项的设计权重乘以样本折减后重新归一化，贡献相加：

```text
maintenance = Σ(normalized_i × effectiveWeight_i)
```

- 有效证据覆盖（折减后设计权重之和）< 45%：`status = "insufficient"`，不输出分数。
- 覆盖 ≥ 80%：高置信。
- 覆盖 ≥ 55%：中置信。
- 其余：低置信。

### 展示阈值（便于核对，不改变上述公式）

- 维护健康度榜单/统计：`maintainedCount` 使用 ≥ 65。
- 列表与详情文字：≥ 75 显示“维护活跃”，≥ 55 显示“平稳”，< 55 显示“放缓/低活跃”。
- 四象限：X=50、Y=60，是组织视图阈值，不是质量及格线。
- “值得关注”面板：维护分 < 45、缺少数据域或命中风险规则。

### 为什么没有 Issue / Release 不扣分

没有 Issue、没有 PR、没有 Release 是项目的真实状态，不能用“零处理量”推断维护差。对应分项会被剔除，因此可解释的证据覆盖会下降。一个只有提交数据的稳定小插件可以仍有维护分，但置信度较低。

## 3. 风险提示

风险等级由公开信号决定，不做风险总分：

- `archived`：高风险信号。
- 长期开放 Issue ≥ 20：高风险信号；≥ 5：需要关注；1–4：信息提示。
- 开放 Issue ≥ 100 或 `openNow/opened90d` ≥ 75%：高风险信号；≥ 50 或 ≥ 50%：需要关注。
- OSV 返回 critical/high：高风险信号；medium/low：需要关注。
- 未完成 OSV 检查、无可靠 npm 下载、数据超过 2 天未更新：数据缺口提示。

若没有任何高风险或需关注信号，且 OSV 精确匹配成功、无公开记录，显示“未见公开风险记录”，而不是“安全”或“零风险”。若 OSV 未完成匹配，则至少为“风险信息不完整”。

**兼容性证据**仅展示 npm 包声明的 `engines.node`、DSH peer range 和版本链接。本项目未安装、未执行插件，也没有运行版本矩阵测试，因此不构成兼容性保证。

## 4. 数据完整度

7 个数据域：仓库基础信息、提交活动、Issue、PR、Release、npm、OSV。

```text
completeness = 可用数据域 / 7 × 100
```

“可用”指本次采集或上一次成功回退确实取得该域的有效响应，不等于该域一定有非零值。没有 Release 的仓库仍可能被标记为 Release 数据域可用（API 成功返回空列表）。没有 npm 包或 OSV 无法精确匹配时，对应域为缺失。

四象限定位条件：

```text
popularity.status = "scored"
maintenance.status = "scored"
npm.status = "verified" 且 downloads30d != null
```

不满足条件的插件进入“未定位”分组，显示原因，不放到原点或任意象限。

## 5. 统计窗口与分母

- Issue：近 90 天创建的非 PR Issue；关闭率分母为其中当前已关闭数 / 创建数。
- PR：近 90 天创建的 PR；合并率分母为合并数 / 创建数。
- Issue 关闭不等于问题解决，PR 合并不等于代码质量高。
- 样本量 < 5（Issue）或 < 3（PR）时降低权重并在页面提示。
- 分页上限触发、接口部分失败时标记为下限或缺失。

## 6. 已知局限

1. 这是公开元数据画像，没有代码审查、测试覆盖率、架构、可访问性或用户体验数据。
2. “维护活动”不是“代码质量”。高频提交也可能来自自动发布或合并策略。
3. Star 与下载都可能被传播、CI、镜像或依赖解析影响；非 npm 分发插件没有下载量。
4. 相对指数会随样本变化；不同方法版本、不同快照不应直接横比。
5. OSV 只覆盖已公开记录；没有记录不等于安全。OSV 详情最多读取 20 条，超过时页面不会声称“完整”。
6. Git 仓库 404、PR 功能禁用、Issue 分页上限和 API 限额都会降低数据完整度。Issue/PR 最多 20 页，触发时按“下限样本”展示。
7. 未安装或运行任何被检测插件，兼容性不做运行时验证。
8. 首次部署后才开始按 6 小时累积历史点；不会补造历史。历史点按方法版本隔离展示。
9. npm range 出现平台性缺数日时，7 日/周变化会被抑制为“不可用”，而不是把缺口当真实 0。
10. `commits30d` 只统计非合并提交；达到分页上限时按已取得的下限计分。

## 7. 方法版本

- `1.0.0`：MVP 初始口径，包含人气、维护、风险、完整度四组输出。
- `1.1.0`：`commits30d` 改为只统计非合并提交；分页上限按已取得数据计分；Issue 积压改为 `openNow/opened90d` 比例并新增开放 Issue 风险规则；Release 只取稳定版；npm 周变化增加日期对齐和平台性缺数日保护；四象限要求 `downloads30d != null`。
- 修改权重、阈值或缺失处理时必须提升 `SCORE_METHOD_VERSION`，并更新本文档与页面方法页。
